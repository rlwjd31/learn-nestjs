# Dependency Injection(의존성 주입) & Inversion of Control(제어의 역전)

service의 instance를 생성한 적이 없는데 어떻게 controller에서 사용할 수 있었을까에 대한 의문이 있다.

이는 NestJS가 백그라운드에서 실행하는 기본 동작원리에 의한 것인데 이를 이해하기 위해서는 `의존성 주입`과 `제어의 역전`에 대해서 알아야 한다.

## 1. 일반 인스턴스 생성

일반적으로 인스턴스는 `new ClassName()`과 같이 생성한다.

```javascript
class A {
  const b = B()
}

class B{
  ...
}

```

## 2. Dependency Injection(의존성 주입)

일반 인스턴스 생성 예시에서 `A는 B에 의존`함을 알 수 있다. 의존성 주입은 `B를 A에서 직접 생성을 하지 않고 외부에서 B instance를 주입`해주는 과정을 말한다. 즉, A가 B를 필요로 하는 상황에 `A가 직접 생성하지 않고 B`를 받아온다.

```typescript
class A {
  constructor(instance: B) { ... }
}

class B { ... }
```

## 3. Inversion of Control(제어의 역전)

class A, B, C가 존재하고 A, C는 B를 필요로 하여 `B에 의존`하는 상황이라고 가정하자.

이 때 A, C는 B를 사용하는 방법이 아래와 같이 `2가지`를 생각해볼 수 있다.

1. A에서 B의 인스턴스를 생성: A 내부에서 B instance를 생성하고 B에 관련된 역할을 수행한다. 즉, `B를 언제 만들고, 어떻게 만들지`에 대한 통제권을 `A`가 가지고 있는 상황으로 `A와 B가 강한 결합`을 가지고 있음을 나타낸다.
2. B의 instance를 A에 주입 시: A가 직접 B의 `생성, 삭제 등`을 수행하지 않고 외부에서 `B의 instance를 생성하여 A에게 주입`하는 방법이다. 즉 B를 `생성, 삭제 등`에 관련한 제어권은 `외부`에게 있다.

2의 방법에서 제어권이 `외부`에 있다고 하였는데 이것이 `제어의 역전`이다. 기존에 `A가 가진 제어권`을 `외부`가 가져온다고 생각하면 이해하기 편하다.

그렇다면 외부를 어떻게 NestJS와 연관을 지을까?

NestJS에서 외부는 `NestJS의 IoC Container`를 뜻한다.

![img](./assets/images/ioc.png '제어의 역전')

1. NestJS는 실행과 동시에 `IoC(Inversion of Control) Container`를 생성한다.
2. class B에 의존하는 곳에 IoC Container가 B의 인스턴스를 생성하여 `A, C가 필요할 때 마다 자동으로 주입`해줌으로써 개발자는 B의 instance의 생성과 폐기를 신경쓰지 않고 `기능에만 집중`할 수 있게 해준다.
3. class A, C는 `controller`, class B는 `Service`라 볼 수 있다. 이 때 `주입을 당하는 주체(class B)`를 NestJS에서는 `Provider`라고 한다.

정리를 하자면 contructor의 인자에 `주입을 받겠다`라고 선언하면 NestJS에 의해 `IoC Conatinaer에서 provider를 찾고 인스턴스를 생성 후 주입`해주는 과정이 background에서 일어나는 것이다.

# Module을 통해 DI & IoC확인하기

현재 `posts.controller.ts`를 보면 `postsService`를 사용하고 있는데 난 주입해준 기억이 없다.

하지만, postsService에 대한 method들을 사용할 수 있었는데 이는 NestJS의 **IoC Container**가 알아서 주입해주는것이다.

```typescript
// posts.controller.ts
@Controller('posts')
export class PostsController {
  constructor(private readonly postsService: PostsService) {}
  ...
}
```

이를 확인할 수 있는 것은 `Module인 posts.module.ts`에서 확인할 수 있다.

```typescript
// posts.module.ts

@Module({
  controllers: [PostsController],
  providers: [PostsService],
})
export class PostsModule {}
```

- `controllers: [PostsController]`: NestJS에서 PostsController를 사용할 것이다라는 명시. 따라서, posts.controller.ts의 내부에 존재하는 `get, post, ...`의 선언이 해당 endpoint에 요청이 들어오면 PostsController로 요청이 들어갈 수 있도록 routing이 되는 것이다. 이는 `PostModule`내에서만 유효하다.

* `providers: [PostsService]` → 이 또한 service 로직(실제로 데이터를 다루는 로직)을 PostModule에 등록하여 NestJS에게 인지를 시키는 것이다. 따라서 이 provider또한 IoC Container에서 관리하여 필요한 곳에 주입을 해준다.
  이렇게 IoC Container는 필요한 컴포넌트들을 가지고 있게 되는데 provider와 같은 경우는 주입당할 수 있는 것을 `@Injectable`을 통해 service내부에 명시해야 한다. @Injectable을 선언함으로써 `provider로서 사용할 됨`을 명시한다.

```typescript
// posts.service.ts
@Injectable()
export class PostsService {
  getAllPosts() { ... }
  getPostById() { ... }
  createPost() { ... }
  ...
}
```

# AppModule & main.ts

NestJS는 모듈들을 어디서 찾아와서 어떤 모듈들을 NestJS에서 관리해야하는지 알고 있을까???

분명히 등록을 해주어야 할 수 있을까 생각이 되는데 이는 `app.module.ts`에서 확인할 수 있다.

`PostModule`을 등록을 해 주었기 때문에 `posts와 관련된 module, controller, service`를 NestJS가 관리할 수 있는 것이다.

```tsx
@Module({
  imports: [PostsModule],
  controllers: [AppController],
  providers: [AppService],
})
export class AppModule {}
```

이 모든 것을 `nestcli`가 자동으로 해준 것이다.

그리고 appModule은 `main.ts`에서 실행을 해준다.

따라서, AppModule로 부터 모든 Module들이 확장해 나감으로써 프로젝트를 구성할 수 있다.

```tsx
AppModule -> PostsModule
               ㄴ PostsController
               ㄴ PostsService
          -> 다른 Module
               ㄴ controller ...
               ㄴ service ...
```
